# 다음 결정과 준비 작업

## 1. 현재 확정한 경계

| 항목 | 현재 결정 |
|---|---|
| 작업 목적 | 기존 결과를 저장하고 팀 공동 개발의 준비·정리를 수행 |
| 코드 기준 선택 | 차이를 먼저 본다. 세 버전은 보존하고 최종 개발 시작점은 아직 확정하지 않음 |
| 구현 | 지금 시작하지 않음. MVVM 전환·화면 숨김·기능 제거도 포함 |
| 노션 | 사용자 요청 전 열람·수정하지 않음. 사용자가 기록·공유하고 싶을 때 따로 요청 |
| 병합·배포 | 커밋·푸시와 별개. 이번 작업에서 진행하지 않음 |

GUI에서 기본으로 표시된 값이나 추천 표시는 사용자 결정으로 취급하지 않는다. 아직 답하지 않은 항목도 임의 확정하지 않는다.

## 2. 남은 결정

아래는 다음 선택지에 넣을 의제다. 이 표 자체로 작업을 승인하거나 선택을 대신하지 않는다.

| 의제 | 선택할 내용 | 현재 제안 |
|---|---|---|
| 개발 기준 | 후보에서 시작 / main에서 필요한 것만 통합 / 추가 대조 | 후보와 회의록을 기준으로 준비하되, 통합은 별도 결정 |
| 지도 | 후보의 언어별 혼합 구조를 유지할지, 다른 제공사 구성을 검토할지 | 현재 사실을 문서화한 뒤 결정. 카카오/NAVER 중 하나로 임의 단순화하지 않음 |
| 개발 환경 | 각자 로컬 / 공용 개발 서버 / 혼합 | 운영 비밀 없이 기본 검사가 가능한 로컬 경로 + 필요 시 공용 개발 API |
| MVVM·상태 관리 | 기존 Controller 확장 / Riverpod 기반 통일 / 일부 병행 | 첫 예제로 비교하고, 전 화면 일괄 전환은 미룸 |
| 첫 공동 예제 | 온보딩 / 장소 저장 / 도슨트 | 장소 상세 → 저장 → 목록 흐름 |
| 공통 지침 | 추적되는 공통 문서와 도구별 진입점, 개인 지침 분리 방식 | 짧은 공유 규칙과 역할별 상세 문서 |
| 과거 문서 | 적용 범위 표시 / archive 이동 / 일부 폐기 | 먼저 대체 관계를 표시하고, 원본 삭제는 별도 선택 |
| 공통 파일 | 라우터·테마·상태·OpenAPI·SQL의 주 리뷰 담당 | 담당표와 변경 전 공유 절차부터 작성 |
| 병합·배포 | 필수 리뷰·CI·운영 승인, 정확한 SHA 배포 | 첫 병합 전에 정하되 지금 설정 변경하지 않음 |
| 제외 기능 노출 | 실증에서 숨김 / 내부 시험만 노출 / 후속 결정 | 지금은 문서만 정리. 구현 때 실증 진입점 숨김을 우선 검토 |

## 3. 다음에 할 준비 작업

| 순서 | 준비 작업 | 결과물 | 아직 하지 않을 일 |
|---|---|---|---|
| 1 | 화면 선별 자료와 온보딩 질문안 대조 | 최소 화면·기능표와 결정 질문 | 화면 구현, 노션 자동 조회 |
| 2 | 현재 규칙과 과거 규칙의 충돌 분류 | AGENTS·문서·개인 스킬의 수정 범위표 | 미선택 지도 규칙 변경, 개인 전역 설정 수정 |
| 3 | 환경과 권한 정리 | 버전·실행 명령·개발 데이터·역할별 접근표 | 클라우드 생성, 운영 비밀 배포, 운영 DB 연결 |
| 4 | API·저장·동기화 경계 설계 | 입력·응답·실패·revision 계약 카드 | API·마이그레이션 구현 |
| 5 | 첫 공동 예제의 구조 선택 | View/Controller/Repository 책임표와 검증 조건 | 전체 MVVM 리팩터링 |
| 6 | 역할별 인계와 리뷰 절차 정리 | 공통 파일 담당표, PR 양식, 완료 기준 | PR 병합, 운영 배포 |

현재 결과물로 1번을 시작할 자료는 갖추지만, 화면 선별 자료와 추가 선택이 필요한 부분은 사용자가 전달하는 자료로 보완한다.

## 4. 지침 정리 대상

| 현재 충돌 | 정리할 방향 |
|---|---|
| 로컬 AGENTS의 카카오 / 템플릿의 NAVER / 후보의 언어별 지도 분기 | 코드 사실과 미래 선택을 나누어 기록 |
| 단일 Mac 운영 지침 / EC2·AWS 런타임 | 현재 개발·운영 환경과 과거 운영 기록 구분 |
| 예전 UI 승인 패킷·개인 이미지·파란색 고정 | 이번 디자인 재량과 보존할 접근성·출처·데이터 원칙 분리 |
| 오래된 기능 정의서가 현재 완료 기준처럼 참조됨 | 기준일·SHA·대체 문서·MVP 범위 연결 |
| 개인 Azure·Orca 스킬이 팀 공통 도구처럼 해석될 가능성 | 프로젝트 공통 작업과 개인 도구 전용 절차 분리 |
| verify 명령 안의 formatter·환경 로딩·검사 생략 | check/fix/live/deploy를 구분한 안내 |

공통 지침에 남길 것은 데이터·인증·시크릿 보호, 현재 작업 범위, 안전한 검증 경로다. 단순히 제약이 많다는 이유로 보안·권한 경계를 없애지 않는다.

## 5. 준비 완료 판단

- 모든 역할이 같은 기준 SHA와 첫 실증 범위를 설명할 수 있다.
- 새 에이전트가 노션이나 개인 이미지에 접근하지 않고도 필요한 문서를 찾을 수 있다.
- 운영 비밀 없이 수행할 검사와 실제 개발 환경이 필요한 검사가 분리돼 있다.
- API·DB·UI가 함께 바뀌는 지점과 주 리뷰 담당이 명확하다.
- 첫 기능의 계층 책임과 성공·실패 검증 조건이 문서에 있다.
- 구현을 시작하는 사용자의 별도 지시가 있다.

실제 새 팀원 환경이나 전체 앱 동작을 이번 문서 작성만으로 검증 완료 처리하지 않는다.
