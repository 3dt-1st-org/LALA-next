# 역할별 인계·검증 시나리오·착수 조건

상태: **독립 준비 갱신 / 팀 채택과 구현 착수 대기**. 네 역할은 기존 회의의 주도 분야이며 독점 권한이 아니다. 아래 세부 작업·리뷰 배정과 소요 시간은 준비 제안으로, 실명·개인 일정이나 팀의 수락을 대신 기록하지 않는다.

## 1. 진행 순서

자료 수령 전 가능한 환경 조사·코드 추천·MVVM 추천·공통 지침 적용 준비는 2026-09-10에 갱신했다. 자료 수령 후 화면 범위 확정 → 환경 접근·최종 코드 SHA 합의 → MVVM 채택 → 공통 지침 활성화·분야별 인계 순서로 결정한다.

| 작업 | 입력 → 결과물 | 선행 조건 | 주 담당 / 리뷰 | 완료 조건 | 예상 작업량 |
|---|---|---|---|---|---|
| P-01 화면 대조 | 선별 PDF·질문안·36개 카드 → 포함 기능·충돌 목록 | 새 자료 수령 | 프론트·백엔드 / PM·기술 리드 | 출처·세부 범위·상태·검증 공백 기록 | 0.5~1일 |
| P-02 제품 결정 | P-01·Q-01~08 → 최소 흐름·필수 상태 | P-01 | 개발 담당 / PM | 첫 화면·투어·설정 범위 합의 | 1회 검토 |
| P-03 공통 지침 | 기존 규칙·수정안 → 채택본·적용 절차 | 준비 완료, 활성화는 P-02·04·05·07 결정 후 | 기술 리드 / 개발 담당 | 5파일 적용·개인 지침 분리·도구별 새 세션 확인 | 0.5일 |
| P-04 환경 인수 | GitHub dev 구성·접근 불일치 → 환경 카드·현재 상태 보고서 | 올바른 배포 구독 접근 또는 상태 보고서 | 기술 리드 / 백엔드·프론트 | 주소·분리·계정·SHA·DB readiness 확인 | 0.5~1일, 접근 대기 제외 |
| P-05 코드 기준 | 후보 조건부 추천·PR 스택 → 최종 SHA·통합 목록 | P-02·04 | 기술 리드 / 백엔드·프론트 | #187→#206 정리, 정확 SHA·선택 이유·검증 기록 | 0.5일 |
| P-06 계약·상태 | 기존 API·기기/계정 경계 → 계약 카드·상태 전이 | P-02, 두 기준 비교 가능 | 백엔드·프론트 / 기술 리드 | 성공·실패·계정 전환·revision 설명 일치 | 0.5~1일 |
| P-07 MVVM 선택 | 장소 저장 A안 추천·B안 재검토 조건 → 채택 기록 | P-05·06 | 프론트 / 기술 리드·백엔드 | Repository·ViewModel 경계, 공존·검증 기준 합의 | 1회 검토 |
| P-08 분야별 로드맵 | 위 결정 → 작업 의존 관계·리뷰·인수 목록 | P-03~07 | 각 역할 / 기술 리드·PM | 착수 항목별 입력·결과·소요·완료 조건 기록 | 역할별 0.5일 |

작업량은 문서 준비의 초기 추정이다. 회신·팀 일정·서버 구축·실구현 시간을 포함하지 않으며 출시일 약속이 아니다. 기술 기준이 미결정이면 그에 의존한 구현 일정을 확정하지 않는다.

## 2. 공통 파일과 리뷰 담당 제안

| 영역 | 주 리뷰 | 함께 확인할 역할 |
|---|---|---|
| 라우터·탭·디자인 토큰·공통 UI | 프론트 | 관련 기능 담당·PM(제품 범위) |
| API router·schema·OpenAPI·Dart adapter | 백엔드 | 프론트·기술 리드 |
| 공유 store·계정 lifecycle·Repository 경계 | 기술 리드 | 프론트·백엔드 |
| SQL 번호·호환성·데이터 초기화 | DB·인프라 | 백엔드 |
| 환경·권한·workflow·배포 대상 SHA | 기술 리드 | 백엔드·PM |
| 실증 지표·피드백·데이터 수집 범위 | PM·데이터 분석 | 프론트·백엔드·기술 리드 |

공통 경계를 바꾸기 전에 관련 리뷰 역할과 입력·출력 변경을 공유한다. CODEOWNERS·branch protection·운영 배포 설정의 실제 변경은 이번에 수행하지 않는다. 현재 main CI 성공이 EC2 배포로 연결되고 dev push도 별도 배포 경로를 가질 수 있으므로 둘 다 임의의 검사용 브랜치로 사용하지 않는다.

## 3. PM·데이터 분석 인계

- 목표 행동: 언어·지역을 선택하고 원하는 장소를 찾아 저장한 뒤 다시 확인하거나 도슨트를 듣는다.
- 피드백 질문안: 다음 행동을 찾기 쉬웠는가, 저장 위치를 다시 찾을 수 있었는가, 장소 설명을 이해했는가, 위치·로그인 실패 후 계속할 수 있었는가.
- 측정 후보: 진입 완료, 장소 상세 열기, 저장/해제 결과, 저장 목록 재방문, 도슨트 재생 시작·실패·완료, 자동 안내 설정 변경.
- 최소 속성 제안: 이벤트 종류, 익명 세션 범위, 언어, 앱·API 버전, 성공 여부·정제된 오류 코드. 정밀 위치·이메일·토큰·식이 답변·음성 원문을 기본 수집하지 않는다.
- 성공 기준의 목표 비율·시간·관찰 대상 수·보관 기간·동의 방식은 PM과 기술 담당이 결정한다. 이번에 분석 SDK·이벤트 수집을 구현하지 않는다.
- fixture 기반 관찰과 실제 참가자의 결과를 별도 기록한다.

## 4. 검증 시나리오와 기대 결과

아래는 **후속 구현·인수에 사용할 시험 명세**다. 지금 통과했다고 주장하지 않는다. 현재 구현 보존 여부 확인과 추가 설계 요구를 함께 표시한다.

| ID | 상황 | 기대 결과 / 판정 경계 | 검증 수준·주 담당 |
|---|---|---|---|
| T-01 | 게스트가 상세에서 저장 후 목록 이동 | 같은 ID가 목록에 보이고 방문 상태는 바뀌지 않음 | 상태·widget / 프론트 |
| T-02 | 저장 후 재시작 | 기기 쓰기에 성공한 ID 복원. 손상 데이터는 시작을 막지 않음 | 기기 저장·앱 / 프론트 |
| T-03 | 기기 쓰기 실패 | 메모리 표시와 영속화 성공을 구분. 성공 문구·재시도 정책 확인(R-04) | 저장 adapter·UX / 프론트 |

| T-05 | 게스트 저장 후 계정 연결 | 기존 합집합 동작과 Q-04의 동의·보존 정책을 대조. 미합의면 수용 판정 대기 | 계약·통합 / 백엔드·기술 리드 |
| T-06 | 계정 A 작업 중 로그아웃·B 로그인 | 이전 계정의 지연 응답·대기 쓰기가 B의 상태·권한으로 넘어오지 않음(R-03) | 비동기 상태·A/B 계정 / 공동 |
| T-07 | 저장·해제를 빠르게 반복 | 최종 의도와 UI·계정 결과 일치, 중복 행 없음 | 단위·API·통합 / 공동 |
| T-08 | 해제 요청 실패 후 재연결 | 해제 의도 유실·ID 재등장 여부 확인(R-02). 필요하면 별도 수정·정책 결정 | 재현·통합 / 백엔드·프론트 |
| T-09 | 저장 ID의 장소 정보가 조회 결과에 없음 | ID 보존, 정보 누락 안내, 재조회 경로 제공 | widget·계약 / 프론트 |
| T-10 | 언어·지역 변경 중 이전 조회가 늦게 완료 | 최신 요청 결과만 반영, 저장 ID 불변 | 단위·widget / 프론트 |
| T-11 | 위치 거부·빈 검색 결과·네트워크 오류 | 수동 지역·empty·error·retry가 구분되고 흐름 계속 가능 | UI·실기기 / 프론트 |
| T-12 | ko ↔ en/ja/zh-Hans/zh-Hant 전환 | 제공사·embed·브리지·라벨·출처가 선택한 지도 방향과 일치 | 웹·native / 프론트 |
| T-13 | 자동 도슨트 ON/OFF와 직접 재생 | 직접 재생 유지, OFF에서 자동 시작 억제, 단일 재생 상태 | Controller·실기기 / 프론트 |
| T-14 | 도슨트 재생 실패·재시도·속도 변경 | 실패와 재생 완료 구분. 1배속 기본, 나머지 수치는 합의 후 시험 | Controller·음성 / 공동 |
| T-15 | 취향·여행 설정의 stale revision | 409와 기존 값 보존, timestamp만으로 덮어쓰지 않음 | API 계약 / 백엔드 |
| T-16 | 공용 API/DB 불가·인증 실패 | 빈 성공·저장 완료로 위장하지 않음. 정제된 코드로 실패 분류 | 계약·통합 / 백엔드 |
| T-17 | 보류 기능 관련 공통 코드 | 이번 문서 변경으로 경로·탭·feature flag·서버 권한이 달라지지 않음 | Git diff / 기술 리드 |

지도·실 Logto·기기 저장·음성 품질·실제 DB 격리는 단위 테스트만으로 인수하지 않는다. 향후 live 검증은 승인된 개발 환경·시험 계정·정확 SHA로 진행한다. 특히 /me 계열 GET의 provision 쓰기를 읽기 전용 조회로 오해하지 않는다.

## 5. PR·인계 카드 양식

작업마다 다음 내용을 채운다. 구현 PR은 선택한 기능의 사용자 행동을 기준으로 작게 나누며 문서 준비 PR과 구분한다.

- 문제와 결과 행동:
- 입력 자료·결정 ID·정확한 기준 SHA:
- 산출물·담당 역할·리뷰 역할:
- 선행 작업·다음 역할에 전달할 계약:
- API·Dart adapter·DB·공유 상태 영향:
- 화면 변경·접근성·출처 확인:
- 실행한 검사와 결과 / 미실행·차단된 검사:
- 데이터 준비·migration·배포 필요 여부와 담당:
- 완료 조건·예상 소요·남은 결정:

커밋·푸시와 PR 병합·운영 배포는 같은 승인이 아니다. 검증한 SHA와 배포할 SHA를 연결하고, DB 변경이 있다면 호환성·적용·복구 순서를 별도 인계한다.

## 6. 착수 판정

| 항목 | 현재 상태 | 닫는 조건 |
|---|---|---|
| 화면 자료·질문안 | 수령 대기 | 원본 식별·36개 카드 연결·최종 범위 합의 |
| 지도 방향 | 사용자 선택 확정 | 선택 코드에서 필요한 변경·웹/native 검증 항목 인계 |
| 개발 기준 SHA | 후보 조건부 추천, 최종 SHA 미확정 | #187→#206 정리·통합 목록·최종 SHA·검증 기록 |
| 공용 개발 API | GitHub 구성 확인, 배포 구독 접근 차단·가동 미검증 | 올바른 접근 또는 상태 보고서, 환경 카드·시험 데이터·담당 확인 |
| MVVM 방식 | 첫 예제 A안 추천, 팀 채택 대기 | Repository + 주입형 ChangeNotifier ViewModel 범위와 재검토 조건 승인 |
| 공통 지침 | 적용 5파일·검증 절차 준비 | 채택·개인 원본 보존·추적·도구별 새 세션 확인 |
| 역할·검증 | 제안 작성 | 각 역할 수락·완료 조건·소요 확정 |
| 구현 착수 | 대기 | 위 선행 조건과 사용자의 구현 지시 |

준비 문서 검수 결과는 [검증 기록](11-validation.md)에 남긴다. 문서 작업이 끝나도 이 표의 미결정·미확인은 남기며 **준비안 작성 완료 / 구현 착수 대기**로 보고한다.
