# 첫 실증 범위와 역할별 인계

9/8 회의록 중 개발에 필요한 결정만 정리했다. 개인 일정·사업 서류·대화 원문은 포함하지 않는다. 사용자가 별도로 전달한 설명도 반영했으며, 노션을 새로 열어 확인한 자료는 아니다.

후속 사용자 선택과 구체적인 준비안은 [화면 대조](06-screen-selection.md)·[결정 기록](03-next-decisions.md)·[역할별 인계](10-role-handoff-and-acceptance.md)를 따른다. 회의 방향이 화면 세부 채택이나 구현 완료를 뜻하지 않는다.

## 1. 첫 실증에서 만들 흐름

| 흐름 | 화면 ID 참고 | 회의 방향 | 착수 전에 준비할 것 |
|---|---|---|---|
| 진입·초기 설정 | S-01~S-06 | 로그인/게스트 → 국가·언어 → 여행 스타일. 한국 방문 외국인 중심 | 온보딩 질문, 위치 거부 경로, 처음과 재진입 흐름 |
| 장소 탐색·결정 | S-10~S-15 | 주변 탐색과 다른 지역 여행 계획, 장소 상세와 저장 | 첫 화면·지역 선택, 필수 장소 정보, 빈 결과·오류·재시도 |
| 저장·투어 | S-20·S-22~S-25 | 단순 저장 우선. 가고 싶은 장소와 방문 상태 구분 | 장소·투어·여행 ID, 저장 단위, 생성·편집의 첫 버전 범위 |
| 도슨트 | S-30·S-57 | 직접 선택 재생과 자동 안내 ON/OFF 유지 | 자동 안내 조건, 단일 재생 상태, 실패·재시도, 설정 저장 |
| 기본 개인화·계정 | S-50~S-59 중 필요한 화면 | 계정·동의·기본 취향·기기 저장·자동 동기화 방향 | 설정 항목 선별, 계정 전환, 서버/기기 데이터 경계 |

화면 ID는 후보 목록을 연결하는 참고 번호다. 위 범위에 포함됐다고 해당 번호의 모든 세부 기능을 구현하기로 확정한 것은 아니다.

## 2. 이미 정해진 방향

- 한 기능을 프론트·백엔드·DB가 함께 만든다. 기존 A-D 독립 플로우 분담안은 현재 역할 기준이 아니다.
- 자동 도슨트는 유지하고 사용자가 ON/OFF를 선택한다.
- 도슨트 속도는 기본 1배속, 느리게·보통·빠르게 3단계다. 느리게·빠르게의 정확한 배속은 아직 정하지 않았다.
- 상세 식이·알레르기 등은 첫 진입에 모두 묻지 않고 이후 설정으로 제공하는 방향이다.
- 저장과 방문은 서로 다른 상태다.
- 기본 취향과 이번 여행 설정은 구분한다. 세부 적용·덮어쓰기 규칙은 설계 대상이다.
- 동기화에 timestamp를 남기는 방향이다. 기존 서버 `expected_revision` 계약을 제거하기로 결정한 것은 아니다.
- 특정 파란색과 기존 화면 배치를 고정하지 않는다. 디자인을 새로 구성하되 전체 일관성을 맞춘다.

## 3. 미룬 기능의 보존과 노출

첫 실증에서 미루는 기능은 **날씨 변화에 따른 일정 재계획, Local Signals, 커뮤니티·채팅**이다. 기능 삭제는 결정하지 않았다.

### 현재 준비 단계

- 기존 코드·테스트·문서를 보존한다.
- 첫 실증의 필수 완료 조건에서 제외하되, 공통 인증·저장 등과 얽힌 의존성은 기록한다.
- 라우터·탭·feature flag를 지금 수정하지 않는다.
- 내부 테스트 전용 노출 방식도 지금 구현하지 않는다.

### 구현 단계에 대한 권장안

실증 사용자에게는 제외 기능의 진입점을 숨기고, 내부 시험용 노출이 실제로 필요할 때만 환경별로 분리하는 방식을 권한다. 작은 팀이 당장 별도 실험 메뉴와 권한 체계를 만들 필요는 없다.

이것은 노출 방식에 대한 제안이지, 사용자 선택이 완료됐거나 이미 적용됐다는 뜻은 아니다. 숨김은 보안 조치가 아니므로 기존 서버 인증·접근 제어를 약화시키지 않는다.

## 4. 역할별로 준비할 자료

| 주 역할 | 먼저 정리할 자료 | 다른 역할과 맞출 내용 |
|---|---|---|
| PM·데이터 분석 | 실증 대상, 핵심 가치, 피드백 질문, 성공 판단 기준 | 어떤 행동을 기록할지, 과도한 개인정보 수집 없이 판단할 지표 |
| DB·인프라·기술 리드 | 데이터 관계, 개발/운영 환경표, 공개 빌드 설정과 비밀의 구분, 접근 권한 | API 저장 단위·revision, 개발 데이터, 배포와 DB 반영 경계 |
| 백엔드·비즈니스 로직 | 포함/제외 화면 목록, API 입력·출력·오류 계약, 저장·동기화 처리 규칙 | UI 상태, 장소·여행·계정 식별자, DB 변경과 호환성 |
| 프론트엔드·UI/UX | 온보딩 질문안, 핵심 사용자 흐름, 첫 화면 후보, loading/empty/error 화면 | 필요한 API·데이터, 화면 상태와 이벤트, 디자인 토큰·공통 컴포넌트 |

역할은 주도 분야이며 독점 권한이 아니다. 누가 승인할지와 공통 파일 담당자는 다음 결정에서 정한다. 공개 문서에는 실명·개인 일정 대신 역할로 표기한다.

## 5. 첫 공동 예제로 다룰 후보

**장소 상세 → 저장 → 저장 목록 확인**을 첫 설계 예제로 사용자가 선택했다. 사용자의 핵심 행동이 짧고, UI 상태·API 계약·저장소·DB 경계를 함께 볼 수 있기 때문이다.

기존 저장 API·기기 저장·계정 연결을 두 코드 기준에서 대조한 결과와 설계안은 [MVVM·API 계약](09-mvvm-and-api-contracts.md)에 있다. 서버 저장을 새로 구현하지 않는다. 첫 예제는 선택됐고, MVVM 방식은 비교 후 팀이 결정한다.

## 6. 준비 자료에서 답해야 할 질문

1. 첫 화면은 지도 중심인가, 관광 정보 중심인가? 현재 위치와 다른 여행지는 어디에서 선택하는가?
2. 추천 투어 편집·자유 경로 생성·장소 중심 생성 중 첫 실증에 무엇을 넣는가?
3. 게스트 저장과 계정 저장은 언제 연결되는가? 실패·로그아웃·충돌 시 무엇을 보존하는가?
4. 도슨트 자동 안내의 조건과 속도 수치는 무엇인가?
5. 첫 기능의 성공 조건을 각 역할이 같은 방식으로 설명할 수 있는가?

이 질문에 대한 자료를 먼저 만든 뒤 구현 일정을 정한다. 이전 회의에서 논의된 출시 가능 시점을 확정 일정으로 바꾸지 않는다.
