## 핵심 논의

### 1. 서비스 지표와 DAU

- 많은 분석 테이블과 대시보드보다 핵심 기능에 필요한 최소 데이터부터 준비한다.
- DAU는 단순 앱 실행이 아니라 핵심 고객 행동을 기준으로 삼는다.
- 저장 일정 재열기가 후보로 제시됐으며 정확한 활성 행동·식별·중복 규칙은 아직 정하지 않았다.

### 2. 회원가입과 게스트

- 게스트는 재방문 식별과 계정 연결이 어렵고 회원가입 동기가 약해질 수 있다는 의견이 있었다.
- 회원가입 필수 방향으로 진행한다.
- 기존 게스트 코드 처리와 실제 수집 정보·동의·보관 정책은 후속 결정이다.

### 3. 화면과 사용자 경험

- 국가·언어, 흰색·옥색 디자인, 홈·설정·위치 안내 화면을 공유했다.
- 현재 디자인 방향으로 진행하면서 한국어·영어·일본어·중국어의 화면 넘침을 확인한다.
- 홈 확정과 지도·여행 계획 UI의 구현 범위는 코드 푸시 후 대조한다.

### 4. 개발·검증 환경

- 운영 환경에 직접 연결해 개발하던 방식을 분리할 필요가 있다.
- 로컬 Docker DB·seed → CI DB 통합 검사 → 스테이징 QA → 프로덕션 흐름을 적용한다.
- 현재 CI에는 PostgreSQL 통합 검사가 없고 개발 API·스테이징 인계도 완료되지 않았다.

### 5. DB 도구와 기존 구조

- FastAPI 환경에 맞춰 SQLAlchemy와 Alembic을 사용하기로 확정했다.
- 코드 기준과 실제 DB에는 SQL 068 및 RAG 구조 차이가 있다.
- 기존 canonical SQL을 Alembic으로 전환하는 기준선·적용 이력·복구 방법은 구현 전에 합의한다.
