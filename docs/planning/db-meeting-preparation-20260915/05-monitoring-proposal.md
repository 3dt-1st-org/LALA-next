# 서비스 모니터링 제안과 결정표

상태: **건동 준비안 / 신석·팀 합의 전**. 실제 사용자 행이나 사용량 로그를 집계하지 않았다. 아래 “가능”은 구조상 가능한 후보이며 집계값·데이터 적재·정확성을 검증했다는 뜻이 아니다.

## 신석님께 먼저 보여줄 설명

현재 DB는 “누가 무엇을 저장했고 어떤 날짜에 방문 결과를 남겼는가”를 설명할 수 있다. 다만 해제하면 저장 행이 사라지고, 방문을 다시 확인하면 시각이 바뀐다. 현재 남아 있는 상태를 클릭 횟수·전체 방문 횟수로 세면 의미가 달라진다.

`identity.users.last_seen_at`은 계정 provision이 마지막으로 실행된 시각이다. 모든 사용자 행동을 기록하지 않으므로 DAU 정의로 사용하지 않는다. `docent_scripts`도 원고 캐시이며 누가 실제 음성을 들었는지 기록하는 테이블이 아니다.

추천은 **이용 규모 + 핵심 흐름 이용·성공 여부**를 함께 보는 것이다. 첫 수집 우선순위는 DAU, 상세→저장, 도슨트 실제 재생으로 제안하고, 최종 순서는 신석님이 실증에서 판단하려는 질문에 맞춰 정한다.

## 지표별 현재 가능 범위와 추가 요구

| ID | 판단하려는 질문·지표 후보 | 현재 데이터로 가능한 범위 | 부족한 것·주의점 | 우선순위 제안 |
|---|---|---|---|---|
| M-01 | 연결 계정이 늘었는가 | identity.users.created_at의 신규 LALA 계정 생성 건수·현재 계정 수 | 전체 Logto 가입자 수·게스트 수가 아님. 삭제 계정이 빠지는 조건 정의 | 보조 |
| M-02 | 하루에 실제 이용한 사람은 몇 명인가: DAU | 정확한 집계 근거 부족 | 게스트·인증 사용자 식별, 활성 행동·시간대·중복 규칙 | 1 |
| M-03 | 첫 진입 후 설정을 마치고 탐색했는가 | 기기 온보딩 완료값 | 최초 시작·완료 이벤트와 이탈 분모, 건너뛰기 구분 | 2 |
| M-04 | 탐색에서 상세를 보는가 | 장소·추천 데이터 자체 | 화면 탐색/상세 이벤트. HTTP 요청 수는 화면 조회 수와 다름 | 1의 기반 |
| M-05 | 상세를 본 장소를 저장하는가 | 현재 저장 집합·현재 행의 saved_at | 상세 분모, 저장 성공·해제 이력. 반복 PUT의 changed=false 처리 | 1 |
| M-06 | 일정을 만들고 다시 사용하는가 | 날짜별 저장 일정·updated_at, 현재 slots | 생성/저장/복원/복사 이벤트. 덮어쓴 과거 버전·원본 날짜 정보 없음 | 2 |
| M-07 | 방문 결과를 확인하는가 | 현재 planned/visited/not_visited·이유·confirmed_at | 실제 도착 자동 측정 아님. 결과 수정·재확인 이력 없음. 미기록 슬롯의 분모 필요 | 2 |
| M-08 | 도슨트가 실제로 재생되는가 | 원고 캐시·서버 요청 상태 일부 | 본문/합성/기기 재생 단계별 성공·실패·재시도, 자동/수동 구분 | 1 |
| M-09 | 서비스 연결이 느리거나 실패하는가 | 프로세스 내 HTTP 횟수·시간 합·최댓값·상태 코드 | 장기 수집·재시작/여러 인스턴스 합산 여부 미확인. 현재 지표만으로 p95 계산 불가 | 운영 기반 |
| M-10 | 운영 비용·데이터 갱신이 적정한가 | ops.daily_costs, job_runs, dependency_checks 구조 | 실제 적재 여부 미조회. 클라우드/API 청구와 매핑·중복·통화 확인 | 운영 보조 |

## 먼저 합의할 지표 정의 초안

| 지표 | 추천 정의 초안 | 반드시 정할 조건 |
|---|---|---|
| DAU | 한국시간 00:00~24:00에 탐색·상세·저장·도슨트 중 하나 이상 수행한 고유 분석 사용자 수 | 각 행동의 발생 지점, 게스트 포함 여부, 로그인 연결 중복, 여러 기기, 지연 이벤트 처리. 앱 실행 수는 보조 지표 |
| 상세→저장 전환 | 같은 세션·같은 장소의 상세 조회 단위 중 저장 완료로 이어진 비율 | 세션/시간창, 동일 사용자·장소 중복, 게스트의 기기 영속화 성공과 계정 서버 승인 단계를 구분 |
| 도슨트 재생 시작 성공률 | 재생 시도 중 기기에서 실제 재생 시작을 확인한 시도의 비율 | 사용자 행동 action_id, 자동/수동, 사용자 취소와 기술 실패, 재시도는 원 시도와 별도 식별 |
| 방문 결과 확인률 | 일정의 유효한 장소 슬롯 중 visited/not_visited를 확인한 슬롯의 비율 | 분모 일정 범위·삭제/수정·미배정 슬롯, 현재 결과 기준인지 최초 확인 기준인지 |

사업계획서의 LALA DAU 최대 500명은 목표·산정 가정이다. 이 조사에서 처리 용량이나 1인당 평균 요청량을 측정하지 않았다. 이후 행동 이벤트와 API 지표를 연결해 `DAU × 1인당 행동 횟수 × 행동별 호출 수`의 가정을 보정한다. 지도 직접 호출·캐시·LLM/음성·재시도는 앱 서버 요청과 따로 센다.

## 최소 이벤트 후보와 수집 위치

이벤트명은 논의용 예시다. API·테이블·수집 SDK를 이번에 추가하지 않았다.

| 이벤트 후보 | 발생 주체·시점 | 성공·중복 기준 |
|---|---|---|
| onboarding_started / onboarding_completed | 앱에서 실제 진입 / 완료 또는 건너뛰기 확정 | 세션·진입 흐름 ID. 화면 재렌더링으로 중복 전송하지 않음 |
| place_explored / place_detail_viewed | 앱에서 결과 표시 / 상세 화면 표시 | 사용자 의도에 따른 화면 사건. 지도 이동마다 HTTP 1건을 같은 행동으로 세지 않음 |
| place_save_completed / place_unsave_completed | 기기 영속화·서버 승인 각각의 완료 지점 | action_id와 stage를 분리. 같은 완료 이벤트 재전송은 event_id로 제거 |
| plan_generated / plan_saved / plan_reused | 생성 응답 수신·저장 승인·복사 확정 | 생성과 저장을 합치지 않음. 원본/대상 날짜 필요성은 수집 범위 검토 |
| docent_attempted / docent_play_started / docent_play_failed | 앱의 사용자/자동 시도·플레이어 콜백 | script/audio HTTP 200을 실제 재생 성공으로 쓰지 않음. stage·bounded error_code |
| visit_feedback_confirmed | 사용자 방문 결과 저장 완료 | 같은 슬롯의 수정과 반복 전송 구분. 시각은 실제 도착 시각과 별도 |

공통 필드의 최소 후보는 `event_id`, `event_name`, `schema_version`, `occurred_at`, `received_at`, `actor_type`, 비식별 분석 사용자 ID, `session_id`, `app_build_sha`, `platform`이다. 필요한 이벤트에만 `action_id`, `stage`, `result`, `request_id`, 요청/실제 제공 언어, 제한된 오류 코드 등을 붙인다. 장소 ID·날짜·재생 시간은 목적과 수집 범위를 정한 후 선택한다.

`request_hash`/`cache_key`는 같은 요청 내용에서 반복되는 결정적 값이므로 사용자나 행동의 고유 ID로 쓰지 않는다. IP·정확한 위치·원문 취향·알레르기·토큰을 기본 이벤트 속성으로 넣지 않는다. guest ID의 재설치/기기 변경 한계와 로그인 연결 규칙은 명시한다.

## 선택지와 권고

| 안 | 장점 | 한계 | 권고 |
|---|---|---|---|
| 기존 업무 테이블만 집계 | 추가 수집 구현이 적음 | 현재 상태 위주. DAU·전환 분모·재생 성공을 설명하기 어려움 | 초기 현황 보조표로 활용 |
| 기존 테이블 + 필요한 최소 행동 이벤트 | 핵심 사용자 흐름의 규모·완료·실패를 함께 설명 | 이벤트 계약·기기/서버 수집·집계 담당 필요 | 추천 |
| 상세 행동 전체 수집 | 이후 다양한 분석 가능 | 초기 설계·검증·보관 부담이 큼 | 현재 착수안으로 권하지 않음 |

## 회의에서 채울 결정표

| 결정 질문 | 추천 출발점 | 결정 상태 | 신석님 피드백·확정값 | 주 담당·리뷰 |
|---|---|---|---|---|
| 어떤 판단을 위해 어떤 지표 3개를 먼저 볼 것인가 | DAU / 상세→저장 / 실제 재생 시작 | 미결정 | 회의 기입 | 신석 / 전원 |
| DAU의 활성 행동·집계일·식별 규칙 | 위 정의 초안 | 미결정 | 회의 기입 | 신석·건동 / 진희·찬혜 |
| 추가 수집 이벤트와 속성·보관 범위 | 지표에 필요한 최소 항목 | 미결정 | 회의 기입 | 건동·진희·찬혜 / 신석 |
| 지표를 어디에서 얼마나 자주 볼 것인가 | 초기 주간 검토표부터, 대시보드 도구는 이후 | 미결정 | 회의 기입 | 신석·건동 |
| 수집·적재·집계·화면 책임은 누가 맡는가 | 앱 찬혜 / API 진희 / DB·집계 건동의 제안 | 미결정 | 회의 기입 | 세 개발자 상호 리뷰 |

회의 후에는 지표마다 `정의 → 분모·분자 → 원천 데이터 → 수집 지점 → 보관 → 담당 → 검증 예시`가 채워져야 구현 항목으로 바꾼다. 표에서 담당 이름이 있다는 사실만으로 수락·완료로 표시하지 않는다.
